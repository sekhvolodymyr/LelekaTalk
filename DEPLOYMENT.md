# Розгортання на Vercel

Production: https://lelekatalk.vercel.app. Supabase: проєкт `LelekaTalk`, ref `oocgzmknsefzfeexpglq`, регіон `eu-central-1`; створений на підтвердженому тарифі $0/місяць.

`api/index.mjs` — Node.js Function для Vercel; vercel.json спрямовує до неї запити. Кореневий `server.mjs` дозволяє запустити той самий хмарний адаптер вручну. `phase-one/server.mjs` і команда `npm start` залишаються локальним файловим варіантом. Потрібен Node.js 24.

## Конфігурація

- Коренева директорія проєкту: корінь репозиторію, без окремого frontend build.
- Runtime: Node.js, регіон `fra1` (Франкфурт).
- Постійне сховище: Supabase Postgres. Дані у приватній схемі `leleka_private`; браузер не підключається до цієї таблиці через Data API.
- `DATABASE_URL` або `POSTGRES_URL`: серверний секрет підключення; не додавати в Git.
- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`: стабільні ключі Web Push та HTTPS-адреса сервісу. Приватний ключ зберігається лише на сервері; у Git його не додавати. Без ключів кнопка push показує, що сервіс не налаштовано.
- `APP_ORIGIN`: канонічний HTTPS-origin, наприклад `https://lelekatalk.vercel.app`. Адреси поточного deployment та основного домену Vercel також беруться із серверних змінних Vercel.
- Preview deployment не підключати до production-бази. Для нього потрібна окрема тестова база; без бази API поверне 503, щоб не створювати тимчасові акаунти.

Проєкт Supabase створюється в організації, яку обрав користувач, після підтвердження вартості. Для Vercel використовується Supavisor transaction pooler (IPv4, порт 6543) з перевіреним TLS. Власна автентифікація LelekaTalk збережена.

TLS перевіряє ім'я хоста та офіційний кореневий сертифікат Supabase у `certs/supabase-prod-ca-2021.crt` (отриманий з https://supabase-downloads.s3.amazonaws.com/prod/ssl/prod-ca-2021.crt, чинний до 26 квітня 2031). Сертифікат включений у серверну Function; це публічний CA, а не секрет. Для цього проєкту перевірено pooler `aws-1-eu-central-1.pooler.supabase.com`.

`LELEKA_DATABASE_BOOTSTRAP=false` вимикає створення схеми сервером: таблиця та права готуються міграцією. Сервер підключається окремою роллю з правами лише SELECT/UPDATE цього стану. RLS дозволяє цю роль; anon/authenticated і PUBLIC не отримують доступу. Пароль ролі та DATABASE_URL додаються лише до серверних секретів Vercel.

## Збереження та транзакції

Перший хмарний MVP зберігає той самий стан модулів у JSONB-рядку Postgres, без перенесення локальних акаунтів. Зміни виконуються у транзакції з `SELECT FOR UPDATE`, щоб паралельні інстанси не перезаписували дані один одного. Успішна відповідь і cookies надсилаються лише після commit. Помилка сховища повертає 503, а не успішну реєстрацію.

Драйвер використовує обмежений пул з'єднань. Для реального навантаження потрібно нормалізувати колекції в окремі таблиці та додати індекси: один JSONB-рядок — сумісний адаптер для першого MVP, а не архітектура масштабного месенджера.

Паролі й токени сесій залишаються хешованими, приватні повідомлення — зашифрованими. Авторизаційні ліміти зберігаються між інстансами. Cookies мають Secure; origin запитів перевіряється. Деталі помилок з секретами бази не виводяться користувачу.

Криптографічний модуль отримує `serverTime` через автентифікований endpoint `/api/mvp/crypto` та відраховує час монотонним таймером браузера. Нові ключі й підписи датуються на 5 секунд раніше для врахування мережевої затримки; перевірка ключів і підписів залишається увімкненою. Це усуває відхилення ключів через годинник пристрою, що випереджає сервер. Кнопки дій блокуються до завершення попередньої операції, зокрема під час повторного рендерингу.

## Перевірки

`npm test` з кореня запускає 23 тести: 14 тестів модулів, 4 тести хмарного адаптера та 5 тестів push. Після deploy слід перевірити реєстрацію, вхід, спілкування двох акаунтів, збереження після повторного запиту та криптографічні ресурси за HTTPS.

## Push та смайли

Підписка вмикається користувачем кнопкою «Увімкнути сповіщення» і прив'язана до браузера та поточного входу. Вихід видаляє підписку сервером, відписує браузер і закриває його попередні сповіщення. Service worker додатково перевіряє поточний акаунт перед показом. Підписки й коротка черга доставки зберігаються в тому самому приватному стані Supabase; додаткові публічні таблиці не потрібні.

Зашифроване повідомлення та записи черги зберігаються однією транзакцією. Після COMMIT Function завершує HTTP-відповідь і очікує спробу Web Push поза блокуванням бази. Черга має термін 5 хвилин, до 4 спроб та оренду для захисту від паралельної доставки; 404/410 видаляє недійсну підписку. Повторні спроби запускаються наступною API-активністю, окремого фонового планувальника немає. Доставка залежить також від підтримки браузера, дозволів та налаштувань ОС. [Документація Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).

Push містить лише ідентифікатори чату/одержувача та мову. Текст повідомлення, ім'я відправника й ключі розшифрування не передаються. Натискання сповіщення відкриває відповідний доступний чат. Новий service worker активується одразу, щоб старі відкриті вкладки не затримували появу push.

Панель Unicode-смайлів містить 5 категорій, пошук українською та англійською і вставлення в позицію курсора. Вибрані смайли шифруються як частина повідомлення.

Браузерна перевірка на 1440×900 та 390×844 підтвердила пошук, категорії, вставлення й передачу смайлів, Escape, увімкнення/вимкнення push, нативний показ сповіщення service worker, перехід у чат і очищення після виходу. Транспорт провайдера у цій автоматизації підмінено; перевірка доставки через FCM/APNs на фізичному Android/iOS не проводилася.

Під час підключення перевірено 8 паралельних записів через два окремі пули та відкат невдалої транзакції у справжній базі Supabase. Security advisor Supabase не повернув зауважень до конфігурації бази; це не замінює аудит застосунку.

Повний аудит безпеки, email-підтвердження, скидання пароля, моніторинг/резервування та навантажувальні перевірки ще не проведено. Обмеження криптографічної схеми й інших модулів наведені в `phase-one/README.md`.
